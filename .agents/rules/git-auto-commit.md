# Regla: Revisión, commit, push y merge obligatorios

- **Alcance:** Todos los agentes, en cada sesión y tras cambios significativos entre pasadas.
- Revisa el estado y el diff completo de los cambios propios, incluidos archivos nuevos; corrige los problemas encontrados y realiza las verificaciones pertinentes. No dejes cambios propios sin revisar. Conserva los cambios ajenos y registra las limitaciones reales.
- **Antes de cada push:** Actualiza las referencias remotas e inspecciona los checks y workflows requeridos de la rama de destino y su SHA actual en GitHub. Si el SHA no tiene ejecución por filtros de rutas, consulta la ejecución aplicable más reciente y deja constancia de la ausencia; no la presentes como un check del SHA actual. Espera los controles pendientes y analiza cada fallo, incluso si parece intermitente o preexistente. Reproduce, identifica y corrige su causa cuando esté en el ámbito autorizado; ejecuta localmente los mismos controles aplicables de CI sobre los cambios preparados y corrige cualquier fallo antes de subirlos. No subas cambios ordinarios mientras la comprobación previa siga roja, pendiente o sin evidencia suficiente.
- **Correcciones de CI:** Si reparar un check requiere publicar un commit para que GitHub lo ejecute, prepara y verifica localmente primero una corrección limitada a ese fallo; solo ese push de reparación es admisible mientras la rama de destino esté roja. Supervisa el SHA publicado, corrige lo necesario y continúa con los demás cambios únicamente cuando los controles requeridos estén en verde. No llames arreglado a un fallo solo por reintentar una prueba intermitente: investiga y corrige su causa, o documenta con evidencia concreta por qué depende de un bloqueo externo y conserva los cambios sin publicar.
- Selecciona solo los cambios propios, crea un commit descriptivo, haz push a `origin` y comprueba que el remoto contiene el commit. Si no hay cambios propios, no crees un commit vacío.
- **Checks de GitHub obligatorios tras cada commit/push:** Comprueba los checks y workflows de GitHub del commit publicado (`powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/Invoke-Gh.ps1 run list --commit <sha>`, `task gh:ci:watch` o `gh pr checks`). Si un check falla por código, tests, assets o configuración, inspecciona `gh run view <id> --log-failed`, corrige la causa raíz, valida en local, sube el arreglo y vuelve a comprobar hasta quedar en verde. Si el fallo es un bloqueo externo (p. ej. cuota/facturación de GitHub Actions), informa el motivo exacto sin declararlo aprobado.
- Toda rama creada para la tarea debe integrarse en su rama de destino: actualiza la base, resuelve conflictos, revisa el diff final, verifica los checks requeridos y haz merge. Confirma que el commit integrado está en la rama de destino y que su publicación y CI terminaron correctamente. Usa un PR cuando corresponda.
- La instrucción explícita del usuario prevalece. Si faltan permisos o remoto, hay conflictos sin resolver, verificaciones fallidas o una protección de rama impide el merge, conserva el trabajo, informa del bloqueo y deja constancia exacta de lo pendiente; no declares completada la integración. No incluyas cambios ajenos, secretos ni temporales.
